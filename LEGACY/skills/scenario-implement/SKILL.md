# Scenario Implement — 시나리오 기반 구현

## 왜 이 스킬이 필요한가

"구현해줘"라고 지시하면 에이전트는 쉬운 일만 반복하고, 어려운 연결 작업을 회피하고,
빌드만 통과하면 "완료"라고 보고한다. 54커밋, e2e 0개가 그 결과였다.

이 스킬은 `/scenario`로 만든 시나리오 스펙을 입력받아서,
**검증 가능한 태스크 → 순차 실행 → 중간 점검 → e2e 테스트 → 완료 보고**라는
구조적 강제를 걸어서, "동작하는 코드"만 나오게 한다.

성과의 단위는 **커밋 수가 아니라 동작하는 사용자 플로우 수**다.

---

## 흐름

### 1단계: 시나리오 로딩

사용자가 `/scenario-implement {기능명}` 으로 호출하면:

1. `_scenario/{기능명}/SCENARIOS.md`를 읽는다.
2. 시나리오 테이블 + 구현 명세(DB 변경, API 변경, Go/프론트 코드 등)를 파악한다.
3. 시나리오에 "구현 명세" 섹션이 없으면 사용자에게 알린다. 먼저 `/scenario`로 구현 명세까지 정리해야 한다.

인자 없이 `/scenario-implement`만 호출하면:
- 현재 대화에서 진행 중인 시나리오가 있으면 그것을 사용한다.
- 없으면 `_scenario/INDEX.md`를 보여주고 선택하게 한다.

---

### 2단계: 태스크 세분화

시나리오의 구현 명세를 읽고, **검증 가능한 단위**로 태스크를 쪼갠다.

#### 태스크 세분화 원칙

1. **1 태스크 = 1 검증 가능한 결과물**
   - "방명록 구현" (X) → "v3_guestbook_entries에 side 칼럼 추가" + "psql로 칼럼 존재 확인" (O)
   - 태스크 완료 조건이 "코드를 작성했다"가 아니라 "검증했다"여야 한다

2. **구현 태스크 뒤에 검증 태스크가 따라온다**
   - 구현 태스크 3~5개마다 검증 태스크 1개
   - 검증 태스크가 실패하면 다음으로 넘어가지 않는다

3. **작업 순서는 레이어 순서를 따른다**
   - 시나리오의 "구현 명세 > 작업 순서"에 명시된 순서를 따른다
   - 명시되지 않은 경우: DB → API Contract → 백엔드 → 프론트엔드 → e2e
   - 하위 레이어가 완성되지 않은 상태에서 상위 레이어 작업 금지

4. **마지막 태스크는 반드시 e2e 테스트**

#### 태스크 유형

| 유형 | 접두사 | 설명 | 완료 조건 |
|------|--------|------|-----------|
| DB | `[DB]` | 마이그레이션, 스키마 변경 | psql/curl로 확인 |
| Contract | `[Contract]` | API 스펙, 코드 생성 | 빌드 통과 |
| Backend | `[Backend]` | handler, service, test (TDD) | go test 통과 + curl 확인 |
| Frontend | `[Frontend]` | 페이지, 컴포넌트, 훅 | 브라우저 스크린샷 |
| Verify | `[검증]` | 중간 점검 | 아래 검증 체크리스트 통과 |
| E2E | `[e2e]` | Playwright 테스트 | 전 시나리오 통과 |

#### 태스크 출력 형식

```
=== 태스크 리스트 ({기능명}) ===

T-01 [DB] ...
T-02 [검증] ...
T-03 [Contract] ...
T-04 [검증] ...
T-05 [Backend] ...
T-06 [Backend] ...
T-07 [검증] ...
...
T-XX [e2e] 전체 시나리오 Playwright 테스트

총 {N}개 태스크 ({구현 M}개 + {검증 K}개 + {e2e 1}개)
```

위 형식으로 태스크 리스트를 사용자에게 텍스트로 먼저 보여준다.
그 직후, **같은 응답 안에서** 다음을 순서대로 수행한다:

1. **TaskCreate로 전체 태스크를 실제 생성한다.** 리스트의 모든 T-XX를 TaskCreate로 등록한다.
   각 태스크의 description에는 [유형] 접두사, 구체적 작업 내용, 완료 조건을 포함한다.
2. **첫 번째 태스크(T-01)를 in_progress로 전환**하고 즉시 실행에 착수한다.
3. 별도 승인을 기다리지 않는다. 태스크 리스트 출력 → TaskCreate → T-01 착수가 한 흐름이다.

### 3단계: 태스크 순차 실행

승인받은 태스크 리스트를 TaskCreate로 등록하고, 순서대로 실행한다.

#### 실행 규칙

1. **1 태스크씩 순차 진행**. 태스크 시작 시 TaskUpdate(in_progress), 완료 시 TaskUpdate(completed).
2. **태스크에 명시되지 않은 파일을 수정하지 않는다**. 시나리오에 없는 기능을 추가하지 않는다.
3. **빌드/테스트 실패 시 다음 태스크로 넘어가지 않는다**. 실패 원인을 수정한 후 재시도.
4. **Backend 태스크는 TDD**: 테스트 먼저 작성 → 실패 확인 → 구현 → 통과 확인.

#### 서브에이전트 투입 시 맥락 주입

서브에이전트에게 태스크를 위임할 때, **파일 경로만 알려주는 것이 아니라 핵심 정보를 직접 텍스트로 주입**한다.

필수 주입 항목:

```
[프로젝트 설명]
- 이 프로젝트의 도메인, 기술 스택, 빌드/테스트 명령어

[사용자 의도]
- 이 태스크가 왜 필요한지, 어떤 시나리오의 어떤 행에 해당하는지
- 시나리오 테이블에서 해당 행의 Actor/Action/Result/Edge Case를 직접 복사

[구현 대상]
- 구체적으로 어떤 파일의 어떤 함수를 만들거나 수정하는지

[스키마/타입 정보]
- 관련 DB 테이블 구조, API 요청/응답 타입을 직접 텍스트로 포함

[유의사항]
- 이 태스크에서 특히 조심할 것 (nullable 변경, 제약조건, 기존 컨벤션 등)
- _architecture/ 폴더 수정 금지
- 프로젝트 코드 컨벤션 핵심 사항 (참고할 기존 파일 명시)

[완료 조건]
- 이 태스크가 "끝났다"고 판단하는 구체적 기준
- 빌드 통과는 기본, 추가로 무엇을 확인해야 하는지
```

"이거 해" 식 단문 금지. 서브에이전트는 한 다리 건너 있어 사용자 의도가 변질되기 쉽다.

### 4단계: 검증 태스크

구현 태스크 3~5개마다 검증 태스크가 들어간다.

#### 검증 체크리스트

검증 태스크에서 확인하는 항목:

**A. 시나리오 대비 점검**
- SCENARIOS.md를 다시 읽는다
- 지금까지 구현한 것이 시나리오의 Action/Result/Edge Case와 일치하는가
- 빠진 시나리오 행이 있는가
- 제약조건(글자수 제한, nullable 등)이 실제로 동작하는가

**B. 근원 문서 훼손 점검**
- `_architecture/` 폴더의 파일이 수정되지 않았는가
- 도메인 모델의 invariant가 지켜졌는가
- API 컨벤션(엔드포인트 분류 기준, 이름 마스킹 등)이 준수되었는가
- `_code_convention/` 의 규칙을 따랐는가

**C. 딴 길로 새지 않았는지**
- 태스크 리스트에 없는 파일을 수정하지 않았는가
- 시나리오에 없는 기능을 추가하지 않았는가 (UI 폴리싱, 애니메이션 과잉, 불필요한 유틸 등)
- "이것도 하면 좋겠다"로 시작하는 범위 확대가 없었는가

**D. 빌드/테스트 통과**
- 백엔드: `go test ./...` 통과
- 프론트엔드: `pnpm build` 통과
- 기존 테스트가 깨지지 않았는가

검증 실패 시 → 실패 항목을 수정한 후 다시 검증. 통과할 때까지 다음 태스크 진행 금지.

### 5단계: UI 와이어프레임 원칙

프론트엔드 구현 시 **디자인은 무시**한다. 목적은 "기능이 동작하는지 눈으로 확인하는 것"이다.

#### 와이어프레임 규칙

1. **투박한 기본 요소 사용**: `border: 2px solid #333`, `background: #f0f0f0` 수준. 디자인 시스템의 예쁜 컴포넌트를 쓰지 않는다.

2. **기능 라벨 필수**: 모든 인터랙티브 요소에 기능을 설명하는 텍스트 라벨을 넣는다.
   - 버튼: `[하트 토글 ON/OFF]`, `[공지 작성 - 100자]`
   - 영역: `[피드 영역 - 무한스크롤, 최신순]`, `[고정글 - 최상단]`
   - 상태: `[로딩 중...]`, `[0건: 아직 활동이 없어요]`

3. **기능은 완전하게**: 못생기더라도 기능 자체는 시나리오대로 완전히 동작해야 한다.
   - 모달이 필요하면 못생긴 모달 (border + fixed position)
   - 무한스크롤이 필요하면 실제 무한스크롤 (IntersectionObserver)
   - 폴링이 필요하면 실제 5초 폴링
   - 토글이 필요하면 실제 토글 (상태 반영)

4. **기존 구현과 확실히 구분**: 와이어프레임 컴포넌트는 기존 디자인과 완전히 다른 스타일이어서, 화면만 봐도 "이 부분이 새로 구현된 것"임을 즉시 알 수 있어야 한다.

5. **애니메이션 스케치**: 애니메이션이 필요한 곳은 최소한의 CSS transition으로 의도를 표현한다. 완성형 애니메이션은 구현하지 않지만, "여기에 슬라이드인이 들어간다"는 걸 볼 수 있어야 한다.

### 6단계: e2e 테스트

모든 구현 + 검증 태스크 완료 후, 마지막 태스크로 **Playwright e2e 테스트**를 실행한다.

#### e2e 테스트 작성 기준

시나리오 테이블의 각 행(S-XX)을 테스트 케이스로 변환한다:

```
S-04a → test: 현장 방문자가 메세지 60자 작성 후 전송 → 라운지 피드에 "참석했어요" + LIVE 축하메세지 둘 다 표시
S-04b → test: 메세지 건너뛰기 → "참석했어요"만 표시, 축하메세지 안 뜸
S-07  → test: Host가 공지 101자 → 거부, 100자 → 통과 + 최상단 고정
S-08  → test: 하트 탭 → 카운트 +1, 다시 탭 → 카운트 -1
```

Edge Case 칼럼에 적힌 내용도 테스트 케이스에 포함한다.

#### e2e 완료 조건

- 모든 시나리오 행의 테스트가 통과
- 스크린샷 첨부 (Playwright MCP 또는 저장)
- 스크린샷 없는 완료 보고는 거짓 보고로 간주

---

### 7단계: 완료 처리 + 사용자 보고

e2e까지 통과하면:

1. **시나리오 인덱스 업데이트**: `_scenario/INDEX.md`에서 해당 시나리오에 완료 표시
   ```
   - [x] [Wedding Lounge](wedding-lounge/SCENARIOS.md) — 완료 (2026-05-08)
   ```

2. **최종 보고**: 사용자에게 다음을 포함한 보고
   - 구현한 시나리오 요약 (어떤 S-XX가 동작하는지)
   - 실행한 태스크 수 (구현 N개 + 검증 K개 + e2e 1개)
   - e2e 테스트 결과 + 스크린샷
   - 생성/수정한 파일 목록
   - 알려진 제약사항이나 후속 작업이 있으면 명시

---

## 주의사항

- **태스크 리스트를 보여주고 즉시 착수한다**. 별도 승인을 기다리지 않는다.
- **태스크 리스트에 없는 작업을 하지 않는다**. 범위 확대 금지. "이것도 하면 좋겠다"는 사용자에게 제안만 하고 승인 없이 실행하지 않는다.
- **검증 태스크를 건너뛰지 않는다**. "빌드 통과했으니 검증 생략"은 금지.
- **UI 폴리싱 금지**. 와이어프레임 이상의 디자인 작업은 시나리오에 명시되지 않는 한 하지 않는다.
- **`_architecture/` 폴더 수정 금지**. 설계 문서는 성역이다. 구현이 설계와 맞지 않으면 구현을 고친다.
- **커밋은 사용자 지시 시에만**. 태스크 완료가 커밋 권한을 포함하지 않는다.
- **e2e 통과 전에 완료 보고하지 않는다**. 빌드 통과 ≠ 동작 증명.
