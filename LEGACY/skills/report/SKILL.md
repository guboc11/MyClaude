# Report — 작업 보고 스킬

## 왜 이 스킬이 필요한가

에이전트가 "X 파일을 수정했습니다"로 끝내면 사용자는 뭘 했는지 모른다.
왜 그 작업을 했고, 어떤 판단을 거쳤고, 결과적으로 프로젝트가 어떻게 바뀌었는지를
한눈에 파악할 수 있어야 한다. 이 스킬은 작업 완료 후 사용자가 전체 그림을
빠르게 이해할 수 있도록 서사 흐름으로 보고한다.

## 보고 구조

### 서사 흐름 (줄글)

다음 순서로 자연스러운 줄글을 작성한다:

1. **Why** — 왜 이 작업이 필요했는지 (배경, 문제)
2. **What** — 무엇을 했는지 (작업 대상, 범위)
3. **How** — 어떻게 접근했는지 (방식, 판단 근거)
4. **보완** — 빠뜨린 부분이 있었다면 어떻게 보완했는지 (없으면 생략)
5. **Result** — 최종 결과. 이걸로 뭐가 달라졌는지

### 선택적 구체화

전체 흐름은 요약 수준으로 쓰되, 다음에 해당하면 해당 부분만 구체적으로 설명한다:
- 에이전트가 판단을 내린 부분 (여러 선택지 중 하나를 골랐을 때)
- 예상과 다르게 흘러간 부분 (계획 변경, 예외 상황)
- 사용자가 나중에 이해해야 할 핵심 로직

구체화가 필요 없으면 하지 않는다. 강제하지 않는다.

### ASCII 구조도

프로젝트 구조 중 변경된 부분을 트리로 그린다.
변경 유형을 마킹해서 원래 모양 대비 뭐가 달라졌는지 보여준다.

마킹 규칙:
- `(+)` 새로 추가된 파일/폴더
- `(~)` 수정된 파일
- `(-)` 삭제된 파일/폴더

변경되지 않은 파일은 맥락상 필요한 경우에만 포함하고, 마킹 없이 그대로 둔다.

```
예시:

src/
├── domain/
│   ├── Wedding.ts          (~)
│   └── GiftMoney.ts        (+)
├── api/
│   └── handlers/
│       └── gift-money.ts   (+)
└── types/
    └── gift-money.d.ts     (+)
```

## 흐름

### 1단계: 변경 사항 수집

대화 맥락과 git diff(unstaged + staged)를 내부적으로 확인해서
실제로 무엇이 바뀌었는지 파악한다. git diff는 사용자에게 보여주지 않는다.

### 2단계: 서사 작성

수집한 정보를 바탕으로 Why → What → How → 보완 → Result 순서로 줄글을 쓴다.

작성 기준:
- 전체 5~15문장. 너무 짧으면 정보가 없고, 너무 길면 안 읽는다.
- 코드 한 줄 한 줄 나열하지 않는다. 흐름과 판단을 전달한다.
- 톤은 동료에게 설명하듯. 보고서가 아니라 대화.

### 3단계: 구체화 판단

서사 중 판단이 들어간 부분, 예상과 달랐던 부분이 있으면 해당 부분만 구체적으로 풀어쓴다.
없으면 이 단계를 건너뛴다.

### 4단계: ASCII 구조도 작성

변경된 파일/폴더를 트리로 그린다.
변경이 1~2개 파일뿐이면 트리 없이 인라인으로 언급해도 된다.
변경이 여러 곳에 걸쳐 있을 때 구조도가 빛을 발한다.

## 출력 포맷

```
## 작업 보고

[Why → What → How → 보완 → Result 줄글]

[선택적 구체화 — 있을 때만]

### 변경 구조

[ASCII 트리]
```

## 하지 말 것

- **git diff를 그대로 보여주지 않는다.** diff는 내부 소스일 뿐이다.
- **코드 블록을 나열하지 않는다.** "이 함수를 이렇게 바꿨다"는 diff의 역할이다. 보고는 흐름을 전달한다.
- **모든 부분을 구체화하지 않는다.** 전체는 요약, 핵심만 구체화. 전부 구체적이면 구체적인 게 아니다.
- **형식적으로 채우지 않는다.** 보완할 게 없었으면 보완 섹션을 쓰지 않는다. Result가 자명하면 짧게 끝낸다.
- **변경 없는 파일을 트리에 잔뜩 넣지 않는다.** 맥락상 꼭 필요한 것만.
