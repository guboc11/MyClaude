# Whatcha Think — 정리 & 피드백 스킬

## 왜 이 스킬이 필요한가

/listen으로 에이전트를 경청 모드에 두면, 사용자의 맥락이 충분히 축적된다.
하지만 그 맥락이 대화 안에 흩어져 있으면 쓸모가 줄어든다. /whatcha-think은
그 흩어진 내용을 하나의 구조로 모아서 사용자에게 돌려주는 단계다.

/listen이 "듣기"였다면, /whatcha-think은 "들은 걸 빠짐없이 정리해서 보여주기"다.

## 흐름

### 1단계: 대화 내용 정리

/listen이 시작된 시점부터 /whatcha-think이 호출된 시점까지의 대화를 정리한다.

**정리 원칙:**
- 사용자가 한 말을 빠짐없이 담는다. 에이전트가 중요하다고 판단한 것만 추리는 게 아니라,
  사용자가 언급한 모든 내용을 포함한다. 사용자 입장에서 "내가 한 말이 빠졌네"라는 느낌이 들면 실패.
- 사용자의 원래 표현과 뉘앙스를 존중한다. 지나치게 추상화하거나 에이전트 언어로 번역하지 않는다.
- 포맷은 내용에 맞게 자유롭게 선택한다. 시간순이 자연스러우면 시간순, 주제별이 명확하면 주제별.
  핵심은 읽었을 때 "맞아, 내가 이런 얘기 했지"라고 느껴지는 것.

**정리 시작 표현:**
```
여기까지 들은 내용 정리해볼게요.
```

### 2단계: 심각한 오류가 있을 때만 언급

정리가 끝나면 기본적으로 그대로 넘어간다. 에이전트의 의견이나 제안은 붙이지 않는다.
괜히 피드백을 덧붙이다가 방향이 꼬이는 게 더 큰 문제다.

예외: 사용자가 말한 내용에 명백한 논리적 모순이나 사실 오류가 있을 때만 짧게 언급한다.
"A라고 하셨는데, 앞에서 B라고 한 부분이랑 충돌하는 것 같아요" 정도.
제안, 우선순위 판단, 추가 고려사항 같은 건 넣지 않는다.

### 3단계: 다음 행동 대기

정리와 피드백을 보여준 뒤, 에이전트는 다음 행동을 사용자에게 맡긴다.

```
이걸 기반으로 뭘 하면 될까요?
```

사용자가 지시하면 그때 실행한다. /whatcha-think이 끝났다고 해서
에이전트가 자동으로 무언가를 시작하지 않는다.

## 하지 말 것

- **정리 단계에서 판단을 섞지 않는다.** "사용자가 ~라고 했는데, 이는 ~이므로..." 식으로
  정리 안에 에이전트의 해석을 끼워넣지 않는다.
- **의견이나 제안을 붙이지 않는다.** 심각한 오류가 아닌 한 에이전트의 피드백은 넣지 않는다. 괜히 꼬인다.
- **자동 실행하지 않는다.** 정리 후에 바로 파일 생성이나 코드 작업으로 넘어가지 않는다.
- **과도하게 구조화하지 않는다.** 내용이 3줄이면 3줄로 정리하면 된다. 억지로 섹션을 나누거나 번호를 매기지 않아도 된다.
