# Scenario — 기획 구체화 인터뷰

사용자는 머릿속에 기능의 전체 그림을 갖고 있지만, 말로 꺼내면 40%만 나온다.
이 스킬은 에이전트가 선생님/인터뷰어로서 질문을 던져서 나머지 60%를 끌어내고,
개발자가 바로 코드로 옮길 수 있는 수준의 시나리오 테이블로 정리한다.

## 왜 이 스킬이 필요한가

"~~~를 구현해줘"라고 추상적으로 지시하면 에이전트는 쉬운 일만 골라 하고,
어려운 연결 작업은 회피하고, 동작하지 않는 껍데기만 만든다.
원인은 지시 자체가 "무엇이 동작해야 하는지"를 정의하지 않기 때문이다.

이 스킬은 구현 지시를 내리기 전에 끼워 넣는 **기획 구체화 단계**다.
사용자가 대충 말하면 에이전트가 쪼개고, 빈 칸을 질문으로 채우고,
최종적으로 "이 표대로 구현해"라고 던질 수 있는 시나리오 스펙을 만든다.

## 시나리오 테이블 구조

사용자의 입력을 다음 칼럼으로 쪼개서 표로 정리한다:

| 칼럼 | 설명 | 예시 |
|------|------|------|
| **#** | 시나리오 번호 (S-01, S-02, ...) | S-01 |
| **Actor** | 이 행동의 주체. 역할 단위 | Host, Guest, 비로그인 방문자 |
| **Screen** | 어떤 화면/페이지에서 | 라운지 피드 탭, 방명록 작성 모달 |
| **Action** | 구체적인 사용자 행동 | "축하해요" 버튼 탭, 텍스트 입력 후 전송 |
| **Result** | 행동 결과로 화면에 나타나는 것 | 피드 최상단에 방명록 카드 추가, 토스트 "등록 완료" |
| **Data Flow** | 어떤 데이터가 어디서 어디로 | Guest Web POST /entries → DB → 라운지 피드 GET |
| **State Change** | 시스템 상태가 어떻게 바뀌는지 | guestbook_entries에 row 추가, 피드 캐시 무효화 |
| **Edge Case** | 실패/경계 상황과 그때 보여줄 것 | 네트워크 끊김 → 재시도 토스트, 빈 텍스트 → 버튼 비활성화 |
| **Permission** | 누가 할 수 있고 누가 못 하는지 | Guest만 작성 가능, Host는 삭제만 가능 |

### 기능 특성에 따라 추가하는 칼럼

위 9개 칼럼은 기본이다. 기능 특성에 따라 에이전트가 판단해서 다음 칼럼을 추가한다:

| 상황 | 추가 칼럼 | 설명 |
|------|-----------|------|
| 실시간 반영이 필요한 기능 | **Realtime** | 폴링/웹소켓/SSE 여부, 갱신 주기 |
| 알림이 발생하는 기능 | **Notification** | 누구에게, 어떤 채널로, 어떤 내용 |
| 전환/탐색이 있는 기능 | **Navigation** | 어디서 어디로 이동하는지, 뒤로가기 동작 |
| 입력 폼이 있는 기능 | **Validation** | 각 필드의 제약조건, 최대/최소, 포맷 |
| 목록을 보여주는 기능 | **Sort/Filter/Pagination** | 정렬 기준, 필터 옵션, 페이지네이션 방식 |
| 시각적 피드백이 중요한 기능 | **Visual Feedback** | 로딩 스피너, 스켈레톤, 애니메이션 |
| 멀티 디바이스 기능 | **Cross-Device** | 모바일/데스크톱 차이, 반응형 동작 |

## 흐름

### 1단계: 입력 수신

사용자가 `/scenario` 뒤에 기능 아이디어를 말한다. 길어도 되고 짧아도 된다.

**예시:**
- `/scenario 방문자가 방명록 쓰면 라운지 피드에 보이게`
- `/scenario 호스트가 공지를 올리면 피드 상단에 고정되고 방문자한테 보여야 해`
- `/scenario 아 그러니까 손님들이 들어오면 뭔가 활동이 보여야 하는데...`

### 2단계: 초안 테이블 작성 + 빈 칸 표시

사용자의 입력에서 파악 가능한 내용으로 시나리오 테이블 초안을 작성한다.

**핵심 원칙:**
- 파악 가능한 칸은 채운다
- 추측으로 채울 수밖에 없는 칸은 **"?"** 로 표시한다
- 에이전트가 임의로 결정하지 않는다. 빈 칸은 빈 칸으로 남긴다.

초안 테이블을 보여준 직후, **3단계의 질문**을 바로 이어서 던진다.

### 3단계: 빈 칸 채우기 질문

테이블의 "?" 칸과 아예 누락된 시나리오를 찾아서 질문한다.

**질문 전략:**

#### 전략 1: 빈 칸 지목
"?" 칸을 직접 가리킨다.
> "S-02의 Edge Case가 비어 있어요. 방명록 텍스트가 500자를 넘으면 어떻게 할 건가요?"

#### 전략 2: 양자택일 (Recognition > Recall)
열린 질문보다 선택지를 준다. 사용자가 "이거!" 하고 고르는 게 처음부터 떠올리는 것보다 쉽다.
> "A: 실시간 웹소켓으로 즉시 반영 / B: 30초 폴링으로 갱신. 어느 쪽이요?"

#### 전략 3: 암묵적 가정 드러내기
사용자가 당연하다고 생각해서 말 안 한 것을 찾아낸다.
> "방명록을 '비로그인 방문자'가 쓴다고 했는데, 닉네임은 직접 입력? 카카오에서 가져오기?"

#### 전략 4: 연쇄 시나리오 탐색
하나의 행동 뒤에 이어지는 행동을 묻는다.
> "방명록이 피드에 올라간 다음, 호스트가 그걸 삭제할 수 있어야 해요? 아니면 올라가면 영구?"

#### 전략 5: 개발 필수 체크리스트
기획에서 빠지면 개발 중에 멈추게 되는 항목들을 묻는다:
- 정렬 기준 (최신순? 인기순?)
- 페이지네이션 (무한스크롤? 페이지?)
- 실시간 반영 여부
- 최대 글자수 / 최대 개수
- 중복 방지 (같은 사람이 두 번?)
- 삭제/수정 가능 여부
- 빈 상태 (데이터 0건일 때 뭘 보여줄지)
- 로딩 상태
- 오프라인/에러 상태

**질문 규칙:**
- 한 번에 최대 3개 질문만 던진다. 많으면 사용자가 지친다.
- 가장 중요한 빈 칸부터 묻는다 (Actor, Action, Result가 비어있으면 그게 최우선)
- 사용자가 "나중에", "아직 모르겠어", "패스" 하면 그 칸은 TBD로 남기고 다음으로 넘어간다

### 4단계: 반복 수렴

사용자의 답변을 반영해서 테이블을 갱신하고, 아직 남은 "?" 칸에 대해 다시 질문한다.
"?" 칸이 모두 채워지거나 사용자가 "됐어", "이 정도면 돼", "충분해" 하면 5단계로.

**매 라운드마다 갱신된 전체 테이블을 다시 보여준다.**

### 5단계: 확정 및 저장

시나리오가 확정되면:

1. 최종 테이블을 보여준다
2. `_scenario/{기능명}/SCENARIOS.md`에 저장한다
3. `_scenario/INDEX.md`에 링크를 추가한다

저장된 파일은 이후 구현 지시 시 "이 시나리오 보고 구현해"로 참조한다.

**사용자가 저장을 원하지 않으면 대화 내에서만 유지하고 파일로 쓰지 않는다.**

## 누적 모드

`/scenario`를 같은 대화에서 여러 번 호출하면:

1. **첫 호출**: 새 시나리오 테이블 생성. S-01부터 시작.
2. **이후 호출**: 이전에 정리한 시나리오를 유지하면서 새 시나리오를 추가. 번호 이어서 매긴다.
   - 이전에 S-01~S-05가 있었으면 새 시나리오는 S-06부터.
3. **수정 호출**: "S-03 수정해줘"로 특정 행을 고칠 수 있다.
4. **매 호출마다 전체 누적 테이블을 다시 보여준다.**

누적된 시나리오 전체가 하나의 기능 스펙이 된다.

## 주의사항

- 이 스킬은 **기획 구체화만** 한다. 코드를 작성하거나 파일을 수정하지 않는다 (5단계 저장 제외).
- 에이전트가 임의로 빈 칸을 채우지 않는다. 모르면 "?"로 남기고 질문한다.
- 질문은 대화체로. "이 부분 좀 알려주세요"가 아니라 "이거 어떻게 되는 거예요?"
- 사용자가 길게 설명하면 그 안에서 여러 시나리오를 추출한다. 하나의 입력 = 하나의 시나리오가 아니다.
- 테이블이 너무 길어지면 기능 단위로 그룹핑한다 (예: "방명록 작성 플로우", "피드 조회 플로우").
- 사용자가 "이 정도면 돼"라고 해도 개발 필수 체크리스트(3단계 전략 5)에서 빠진 게 있으면 한 번 더 확인한다.
  단, 사용자가 두 번째로 "됐어"하면 그대로 확정한다. 집요하게 붙잡지 않는다.
