## 무엇을 하는 도구인가

말할 게 많을 때 왕복 대화의 기다림을 없애는 파이프라인이다.

```
사용자 → Listen 패널 여럿 (listen_add — 답하지 않는다)
              ↓ inbox
         batcher (5분마다 자름 / flush로 즉시)
              ↓ queue: b-001 b-002 b-003 …
         Filter 패널 (filter_next → 벼림 → filter_write → filter_done, 대기줄 빌 때까지)
              ↓
         draft.md — 최종안 한 편이 계속 좋아진다
```

Listen은 **넓히는 쪽**(다 받고 조사로 살을 붙임), Filter는 **벼리는 쪽**(연결·중복 제거·갱신·오류 제거).
하는 일이 정반대라 따로 세운다.

## 규율은 프롬프트가 아니라 도구 모양에 있다

- Listen에게는 **읽는 수단이 없다** — draft도, 남의 발화도, 배치도 못 본다. 되묻거나 정리하려는 유혹 자체가 안 생긴다.
- Filter에게는 **inbox를 건드릴 수단이 없다** — 얼린 배치만 본다.
- **어느 도구에도 삭제가 없다.** 이동만 있다: inbox → queue → archive.
- `filter_write`는 changelog 없이는 거부한다.

## 도구 8종

| 도구 | 하는 일 | 누가 |
|---|---|---|
| `listen_add(text, note?)` | 발화를 inbox에 파일 하나로. 조사는 `note`로 분리 저장 | Listen |
| `listen_flush()` | 지금 여기까지 잘라 배치 하나 찍기 | Listen |
| `batcher_on(interval)` | 자동 자르기 켜기 (기본 300초) | 아무나 |
| `batcher_off()` | 끄기 (잘린 배치는 유지) | 아무나 |
| `batcher_status()` | 켜짐·주기·마지막 자른 시각·inbox 건수·대기줄 길이 | 아무나 |
| `filter_next()` | 가장 오래된 배치 + 지금 draft를 함께 꺼냄 (옮기지 않음) | Filter |
| `filter_write(draft, changelog, batch)` | draft 교체 + 옛 판 보관 + diff 생성 + ledger 기록 | Filter |
| `filter_done(batch)` | 배치를 archive로 (두 번 불러도 안전) | Filter |

모든 도구에 `topic`(선택)이 있다. 생략하면 기본 주제.

## 저장 구조

```
.claude/listen/{주제}/
  inbox/          2026-08-02T00-32-20-p1xx.md    한 발화 = 한 파일 (경합 없음)
  queue/          b-003/ b-004/ …                 대기줄
  archive/        b-001/ b-002/ …                 처리 끝난 배치
  draft.md                                        지금 살아 있는 최종안
  draft.history/  v1.md v2-prev.md v2.diff …      판마다 본문 + 앞 판 + diff
  ledger.md                                       판마다 한 줄: 어느 배치 / 무엇을 왜 / 뺀 것
  batcher.json                                    켜짐·주기·마지막 자른 시각
```

## 되짚는 법

판 번호와 배치 번호가 짝이다 (`b-003` → `v3`).

1. `draft.md`에서 미심쩍은 문장을 찾는다
2. `ledger.md`에서 그 내용이 들어온 판(`v3`)과 배치(`b-003`)를 본다
3. `archive/b-003/`을 열면 그 배치의 원본 발화가 전부 있다

"내가 말했는데 없어졌다" 싶으면 ledger의 changelog에 **뺀 것과 사유**가 적혀 있다.

## Listen 패널 운용법

- 사용자 발화를 **전부** `listen_add`로 받는다. 관련 조사가 있으면 `note`에 붙인다.
- **답하지 않는다.** 되묻지 않고, 다듬지 않고, 요약하지 않는다. 맞춤법도 고치지 않는다 — 오탈자도 원문이다.
- 도구를 부른 뒤에는 영수증 한 줄만 말하고 다음 말을 기다린다. 길게 요약하면 사용자의 흐름이 끊겨
  이 도구가 존재 이유를 잃는다.
- 사용자가 "여기까지 끊어줘"라고 하면 `listen_flush`.

## Filter 패널 운용법

`filter_next` → 벼림 → `filter_write` → `filter_done` → 다시 `filter_next`. 대기줄이 빌 때까지 반복한다.

- **요약이 아니라 재구성이다.** 흩어진 것을 연결하고, 중복은 지우고, 뒤 발화가 앞을 개선했으면 갱신하고,
  논리가 어긋난 것은 걷어내고, 필요하면 주석을 단다. 산출은 항목 목록이 아니라 **한 편의 글**이다.
- `filter_write`의 changelog에는 **이번에 뺀 것과 왜 뺐는지**를 반드시 적는다. 벼리는 도구일수록
  뺀 자국이 보여야 믿을 수 있다.
- 대기줄이 비면 쉰다. `filter_next`가 "대기줄이 비었습니다"를 돌려주는 것은 에러가 아니다.

## 시작 절차 — 순서가 중요하다

1. **서버 코드를 고쳤으면 먼저 `/mcp` 재연결.** 이미 떠 있는 프로세스는 옛 코드로 계속 돈다.
   고친 줄 알고 주행을 시작하면 고치기 전 동작을 보게 된다.
2. **패널을 모두 띄운 다음에 `batcher_on`.** 켠 뒤에 패널이 붙으면 그 패널의 서버도 타이머를
   건다(`batcher.lock`이 실제 자르기는 막지만, 순서를 지키는 편이 예측 가능하다).
3. **`batcher_on`을 부른 패널을 도중에 닫지 말 것.** 자르는 권한이 그 프로세스에 있다.
   닫히면 맥박이 끊길 때까지(주기의 2.5배, 5분 주기면 최대 12분 30초) 아무도 자르지 않는다.
   그 패널을 닫아야 하면 다른 패널에서 `batcher_on`을 다시 불러 권한을 옮긴다.
4. 주기는 **5분을 유지한다.** 60초로 돌려본 실측(2026-08-02): 12발화가 배치 7개로 갈려
   평균 1.7발화/배치, 배치 절반이 발화 1~2개짜리였다. Filter가 한 번에 볼 맥락이 얇아진다.

## 패널 편성

Listen 3 + Filter 1을 기본으로 본다. cmux 패널 이름 예: `LISTEN1/2/3: {주제}`, `FILTER: {주제}`.
사용자는 1→2→3→1 순으로 번갈아 던지고, 각 Listen은 자기 차례의 말만 받는다.

패널 구분은 자동이다 — 패널마다 서버 프로세스가 다르고 `CMUX_SURFACE_ID`에서 식별자가 온다.
`listen_add`에 패널을 넣는 인자는 **없다**(한 패널이 남의 이름으로 적을 자리를 만들지 않는다).

Filter를 돌리는 방식(무한 루프로 계속 깨어 있기 vs `/loop`로 주기 기동)은 계획서 §6 쟁점 3 —
첫 실전 주행에서 대기줄 길이 변화를 보고 정한다. 리허설 실측으로는 배치 하나 처리에 약 25초라,
**대기줄이 빌 때까지 돌고 쉬는** 방식이면 5분 주기를 충분히 따라간다.

## 함정

- **자르는 순간의 경합**: `cut()`은 이동 대상을 먼저 스냅샷으로 확정하고 그 목록만 옮긴다.
  스냅샷 이후 들어온 발화는 inbox에 남아 다음 배치로 간다. 이 순서를 바꾸면 발화가 유실된다.
- **패널이 여럿이면 서버 프로세스도 여럿이다.** 패널마다 자기 MCP 서버를 띄우고, 서버가 뜰 때
  `batcher.json`의 `on:true`를 보고 각자 타이머를 건다. 그대로 두면 패널 4개 = 타이머 4개라
  5분 주기가 75초로 무너진다(2026-08-02 실측: 서버 3개 시차 기동 시 배치가 3배로 잘림).
  그래서 `batcher.lock`에 맥박을 남겨 **권한을 쥔 프로세스만 자른다.** 그 프로세스가 사라지면
  맥박이 끊기고 다른 프로세스가 이어받는다. 이 검사를 없애면 주기가 곧바로 깨진다.
  · 타이머 위상이 겹치면 증상이 안 보인다 — 시험할 때 서버를 **시차를 두고** 띄울 것.
  · 서버 코드를 고쳐도 **이미 떠 있는 프로세스는 옛 코드로 돈다.** `/mcp` 재연결이 필요하다.
- **배치 번호**: queue와 archive를 **모두** 훑어 최대값 +1. 폴더는 `recursive` 없이 만들어
  먼저 만든 쪽이 번호를 갖게 한다 — `recursive:true`는 이미 있어도 조용히 성공해서
  두 프로세스가 같은 번호를 나눠 갖는다.
- **changelog 없이 write 금지**: 도구가 거부한다. 우회하지 말 것.
- **시각은 KST 고정**: `toLocaleString('sv-SE', {timeZone:'Asia/Seoul'})`. `toISOString()`을 쓰면
  한국 새벽에 날짜가 하루 밀린다(task-mcp 사고).

## 시험

`node --check`로 문법, 그리고 서버를 stdio로 띄워 `tools/list`로 도구 8개를 확인한다.
단독 주행 시험 스크립트는 세션 임시 폴더에 있었고(무손실·번호 연속·판 정합·원문 보존·빈 상태 검사),
필요하면 같은 각본으로 다시 만들면 된다 — 주제를 `dryrun` 등으로 따로 두고 끝나면 지운다.
