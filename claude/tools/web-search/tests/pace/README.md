# 전역 속도 장부 — 예약이지 확인이 아니다

태스크 `2026-08-12-web-search-MCP-v2-rebuild#24` · 근거 계획: `_PLAN/2026-08-11-web-search-mcp/PLAN.md` 8절

```
node tests/pace/verify.mjs          # 전부 검사 (exit 0 이면 통과)
node tests/pace/verify.mjs --json
```

## 왜 이것만 workspace 밖에 있는가

workspace 는 여럿이어도 상대 서버는 하나다. 조사 세 개가 각자 자기 workspace 안에서 간격을 지켜도,
같은 도메인을 셋이 동시에 두드리면 상대 입장에서는 세 배로 맞는 것이다. 그래서 이 장부만
도구 옆 `runtime/pace.db` 에 둔다.

## 예약과 확인의 차이

**확인은 무너진다.** "마지막 접속 시각을 보고 비었으면 나간다" 는 두 프로세스가 같은 틈을 보고
함께 나간다. 사이에 잠금이 없기 때문이다.

**예약은 무너지지 않는다.** transaction 안에서 다음 허용 시각을 **먼저 밀어 놓고** 자기 차례를
받아 나온다. 받은 시각까지 기다렸다 나가면 되고, 다시 물어볼 필요도 경쟁할 필요도 없다.

`reserve` 는 아무도 되돌려 보내지 않는다(줄이 정해 둔 한계보다 길 때만 예외). 스무 명이 같은 순간에
물어도 각자 다른 시각을 받는다. 되돌려 보내면 모두가 다시 묻게 되고, 그러면 운 나쁜 프로세스가
영영 못 들어가는 자리가 생긴다.

음성 대조 H1 이 이 차이를 실제로 보여 준다. 같은 스무 프로세스를 transaction 없이 돌리면
**60개 자리 중 55개가 겹치고** 정책보다 가까운 쌍이 59개 나온다. 예약으로 하면 0개다.

## 완료 조건 실측

프로세스 20개가 서로 다른 폴더에서 같은 순간에 들어가 3개씩, 모두 60개를 예약했다.

| 잰 것 | 값 |
|---|---|
| 결과를 낸 일꾼 | 20/20 (말없이 죽은 프로세스 0) |
| 예약 | 60/60 · 오류 0 |
| 서로 다른 자리 | 60개 (0~59, 겹침 0 · 빠짐 0) |
| 정책(25ms)보다 가까운 이웃 | **0쌍** · 실제 최소 간격 25ms |
| 서로 다른 주인 | 20명이 한 줄을 나눠 섰다 |
| 첫 자리~마지막 자리 | 1,475ms (= 25ms × 59, 정책이 요구하는 최소치와 정확히 같다) |

주인이 20명이라는 것이 완료 조건의 핵심이다 — workspace 가 달라도 줄은 하나다.

## 403 하나로 오래 자지 않는다

계획서 8절이 "403 한 번으로 몇 시간 자동 휴면하지 않음" 을 요구한다. 1차의 `pace.mjs` 는
차단 낌새가 세 번 쌓이면 세 시간을 재웠다. 조사가 통째로 멈추는데 정작 왜 멈췄는지는 아무도 모른다.

여기서는 갈래를 둘로 나눴다.

- **자동 물러남**에는 천장이 있다(`MAX_AUTO_BACKOFF_MS` = 5분). 실패가 쌓이면 두 배씩 물러나되
  거기서 잘린다. `opts` 로 세 시간을 넘겨도 자동 경로에서는 5분이 된다 — 시험 B2 가 열세 번
  실패시켜 확인한다.
- **차단(403)은 세기만 한다.** `blocked_count` 가 늘 뿐, 그 수를 보고 스스로 재우지 않는다.
- **긴 휴면은 `sleepDomain` 하나로만 들어온다.** 왜 재우는지와 누가 정했는지를 반드시 적어야 하고,
  둘 중 하나라도 없으면 거절한다. 이유 없는 휴면은 나중에 아무도 풀지 못한다.

## 이 장부에 없는 것

item 상태도, 판정도, workspace 이야기도 없다. 시험 D1 이 스키마를 직접 훑어 `item`·`judgment`·
`label`·`work_state`·`lease`·`artifact` 같은 낱말이 든 칸이 하나도 없음을 확인한다.
표는 셋뿐이다 — `pace_meta`, `pace_domain`, `pace_reservation`.

`holder` 칸만 예외처럼 보이는데, 이것은 "누가 이 도메인을 붙들고 있나" 를 보려는 이름표(64자 제한)이지
상태가 아니다. 스무 프로세스가 뒤엉킬 때 이 칸이 없으면 무슨 일이 일어났는지 되짚을 수가 없다.

## 나가는 문은 하나다 — `withPace`

```js
await withPace(db, domain, async (slot) => { /* 여기서 나간다 */ }, { holder, opts });
```

예약하고 · 자기 차례까지 기다리고 · 나갔다 와서 · 결과를 알린다. collect·map·search 가 모두
이것으로 나간다. 길이 하나여야 "예약을 빠뜨렸다" 가 생기지 않는다. 안 쓰고 직접 fetch 하면
그 요청은 장부에 없는 요청이 된다 — #25 부터 이 규율이 붙는다.

안에서 예외가 나가도 실패는 기록된다(F4). 자리를 못 받으면 안쪽 일은 **아예 돌지 않는다**(F5).

## 만드는 동안 실제로 걸린 것

**`lib/db.mjs` 에 게이트 0 과 같은 결함이 남아 있었다.** `applyPragmas` 가 `journal_mode = WAL` 을
`busy_timeout` 보다 **먼저** 걸고 있었다. journal_mode 문장 자체가 잠금을 잡는데 그 시점엔 기다릴
시간이 0이라, 여러 프로세스가 같은 순간에 열면 한 명이 예외로 죽는다. 게이트 0 의 spike 일꾼에서
같은 원인으로 9/10 이 났고 그때 spike 쪽만 고쳤다 — 정작 runtime 은 그대로였다.
pace 를 만들며 같은 pragma 를 다시 쓰려다 발견했다. 순서를 뒤집고 `applyPragmas` 를 내보내
pace 도 같은 것을 쓰게 했다. 게이트 0·1·2 를 다시 돌려 그대로 통과하는 것을 확인했다.

**`undefined` 는 "지정 안 함" 이지 "기본값을 지우라" 가 아니다.** 1차 감사에서 나온 사고를
그대로 옮겨 왔다 — MCP 도구가 선택 인자를 그대로 넘기면 `{min_interval_ms: undefined}` 가 되어
기본값이 지워지고 간격이 `NaN` 이 되어 아예 안 걸린다. A9 가 이것을 지킨다.

## 지금 알려진 한계

- **아직 아무도 이 문으로 나가지 않는다.** `withPace` 는 있지만 collect·map·search 가 없다.
  실제로 네트워크 앞에 붙는 것은 #25 부터이고, 게이트 3 이 "요청 전에 예약했는가" 를 실측한다.
- **간격은 시각으로만 잰다.** 예약을 받고 실제로 나가지 않는 프로세스가 있으면 그 자리는 빈다.
  자리를 반납하는 길은 아직 없다 — 필요해지면 그때 만든다.
- **전역 장부에 #5 spike 의 `spike_pace_domain`·`spike_pace_reservation` 두 표가 남아 있다.**
  새 `pace_` 표와 이름이 겹치지 않아 충돌은 없고, 그 안에도 시각뿐이라 규칙 위반도 아니다.
  치우는 것은 #48(전환)에서 한다.
