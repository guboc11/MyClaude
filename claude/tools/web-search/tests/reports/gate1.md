### 실제 수치

**단위 시험 148항목.** paths 25 · db 26 · workspace-new 18 · url 23 · import 20 · items 19 · status 17.

**URL 1만 건.** JSONL 628,816바이트를 workspace 안에 두고 `add_urls` 로 넣었다. 받은 것 11,001건 →
새로 10,000 · 중복 1,000 · 거절 1, 176ms. 중복 1,000건은 같은 쪽에 추적 파라미터만 다르게 붙인
것이고, 거절 1건은 `ftp://` 다. 응답은 316바이트로 입력의 0.05% — 원문이 실리지 않는다.

**출처 보존.** 같은 세 주소를 다른 출처(`sitemap`)로 다시 넣으니 item 은 10,000 그대로이고
sources 만 10,003 이 됐다. 출처가 둘 이상인 item 이 정확히 3개다.

**표본 전수.** `tests/fixtures/url-samples.json` 의 합침 표본 53개와 갈림 24개를 MCP 로 넣어,
합침 열쇠 3개가 모두 있고 갈려야 할 12쌍이 모두 갈렸으며 빠짐·군더더기 0을 확인했다.
기대 개수를 손으로 어림하지 않고 표본이 말하는 열쇠 집합과 견준다.

**경계.** 절대경로 입력·상위 이동(`../../../etc/hosts`)·workspace 안의 심볼릭 링크를 모두 거절했고,
바깥 파일에 있던 URL 이 장부에 들어간 건수는 0이다. 없는 workspace 를 물으면 `workspace_missing`
오류를 낸다 — 0건 workspace 로 꾸미지 않는다.

**재시작.** 서버를 껐다 새로 띄운 뒤에도 total 10,000 이고 `integrity_check = ok`,
`events.jsonl`·`state.json` 같은 두 번째 장부는 없다.

**git.** workspace 뿌리·`workspace.db`·`artifacts/pages`·`exports` 넷이 모두 `git check-ignore` 에
걸리고 `git status` 노출은 0줄이다. 규칙은 `workspace_new` 가 만들기 **전에** 확인하고 없으면
그때 넣는다.

## 앞 게이트에서 고친 것

게이트 0 독립 재검증에서 SQLite 시험이 간헐 실패한다는 결함을 받았다(감사자 실행에서 200행 대신
180행). **처음 짚은 원인이 틀렸다.** 붐빔에 밀린 삽입을 버려서라고 보고 재시도를 넣었는데, 고친 뒤에도
같은 실패가 재현됐다. 다시 재 보니 진짜 원인은 다른 것이었다 — **일꾼 하나가 아예 결과를 못 냈다(9/10).**

일꾼이 DB 를 열면서 `busy_timeout` 을 걸기 **전에** `PRAGMA journal_mode = WAL` 을 실행하고 있었다.
열 개가 같은 순간에 열면 그중 하나가 잠금에 걸리는데, 그 시점엔 기다릴 시간이 0이라 예외가 나고
일꾼이 아무 말도 못 한 채 죽었다. 180 = 살아남은 9명 × 20줄이었다. 셈은 맞았고(그래서 항등식 검사도
통과했다) 그저 한 명이 사라진 것이었다.

고친 것 셋.

- `busy_timeout` 을 가장 먼저 건다. 그다음 `journal_mode`·`foreign_keys` 를 건다.
- 일꾼이 시작에서 실패해도 조용히 사라지지 않고 `fatal` 한 줄을 남기고 종료 코드 3으로 끝난다.
- 부모가 "몇 명이 결과를 냈다" 만 세지 않고, 시작 실패 사유와 말없이 끝난 자식의 stderr 를 함께 적는다.

붐빔 재시도도 그대로 두었다 — 원인은 아니었지만 실제 워커가 해야 할 일이고, `busy_timeout` 을 1ms 로
줄여 억지로 붐비게 한 실행에서 물러남 12회가 나고도 200행이 모두 들어가는 것을 확인했다.
정상 설정으로 게이트 0 을 **다섯 번 연속** 돌려 모두 10/10 일꾼·200행·exit 0 이다.

## 뒤에 고친 것 — 시점에 못 박힌 검사

게이트 2를 닫은 뒤 독립 재검증에서 이 게이트가 exit 1 로 깨졌다. G1-13 이 "공개 버튼이 정확히
셋" 이라는 **게이트 1 시점의 집합**을 기대했는데, 게이트 2에서 여섯이 되자 어긋난 것이다.
구현된 버튼의 계약 실패는 0이었으니 제품 결함이 아니라 시험이 그날에 못 박힌 것이었다.

살아남는 불변식으로 바꿨다 — "게이트 1의 세 버튼(`workspace_new`·`add_urls`·`status`)이 있고,
공개된 모든 버튼이 계약을 지키며, 미구현 버튼은 공개되지 않는다". 버튼이 몇 개든 성립한다.
게이트 2의 같은 함정(G2-12)도 함께 고쳤다. 고친 뒤 게이트 0·1·2 를 연속으로 돌려 셋 다 exit 0 이다.

이 문서가 약속한 "한 번에 다시 돌리는 법" 과 최종 게이트(#49)의 전 게이트 재실행이 이 성질에
기대고 있으므로, 앞으로도 게이트 검사는 그때의 개수가 아니라 불변식으로 쓴다.

## 지금 알려진 한계

- **버튼 일곱이 없다.** `search`·`map_domain`·`next`·`collect`·`report`·`retry`·`export`.
  계약 시험은 그 일곱에서만 실패하며, 구현된 셋은 계약을 전부 지킨다.
- **`search` 는 미완료로 남는다.** 무키 공급자를 찾지 못했다([decision.md](../spikes/search-provider/decision.md)).
- **네트워크로 나가는 코드는 아직 없다.** `lib/network-policy.mjs` 는 판정만 하고, 그 판정으로
  실제 연결을 고정하는 일은 #25 가 한다. 지금 검사한 것은 판정 함수이지 연결이 아니다.
- **`node:sqlite` 는 실험 기능이다.** `lib/db.mjs` 가 최소 버전을 확인하지만 API 안정성은 보장하지 못한다.
- **`awaiting_report`·`expired_leases` 는 손으로 만든 상태로만 시험했다.** 진짜 임대는 #16·#17 이
  만들고, 게이트 2가 실측한다.
