## 왜 이것만 fixture 인가

일부러 멈추고 끊고 틀린 화면을 받아야 하는데, 그걸 남의 사이트에 대고 하는 것은 예의가 아니다.
무엇보다 **같은 장애가 다시 안 나면 "되찾을 수 있다" 를 증명할 수 없다.** 장애는 만들어야 재현되고,
재현돼야 잴 수 있다. 그래서 다섯 자리를 골라 두었다 — 멀쩡한 쪽 하나, 상태 200 인데 오류 화면,
세 번 넘어가는 쪽, 본문이 영영 안 끝나는 쪽, 서버 오류.

```
node tests/e2e/scenario-c.mjs run --project <프로젝트> --out <record.json>
```

## 이 연습이 실제로 증명한 것

**죽어도 만든 것은 남는다.** 강제 종료 시점까지 만든 산출물 3개가 파일과 장부 양쪽에 그대로 있었다.
파일 먼저 쓰고 장부에 매다는 순서(#23)가 여기서 값을 한다 — 반대였으면 "파일 없는 장부 줄" 이
남았을 것이다.

**죽은 워커의 몫을 남이 함부로 못 가져간다.** 만료 전에는 0건, 만료 뒤에는 5건. 그 사이에
사람이 개입한 것은 없다. 시간만 지났다.

**늦은 보고는 거절되고, 거절이 장부를 바꾸지 않는다.** 만료된 임대로 보낸 판정은
`lease_expired` 로 막혔고 판정 줄은 0 그대로였다. 이 항목은 앞선 판에서 **헛돌고 있었다** —
그때는 빈 임대로 보고해서 "항목이 없다" 는 다른 이유로 거절됐다. 지금은 항목 5건을 쥔 임대가
진짜로 만료돼서 거절된다.

**status 하나로 다음 손이 정해진다.** 오류 갈래·건수·item 번호·실행 번호·빠진 산출물·요약 파일
자리까지 status 응답 안에 있었다. 그걸 그대로 `retry` 에 넣으면 된다.

## 만드는 동안 실제로 걸린 것

**진행기가 21분 동안 멈춰 있었다.** 서버를 일부러 죽여 놓고 그 서버의 답을 기다렸기 때문이다.
손잡이(`mcp-client.mjs`)에는 한 시간짜리 시계밖에 없어서, 부른 쪽은 오지 않을 답을 한 시간
기다릴 참이었다. SUPERVISOR 가 "20분째 무진행" 을 관찰해 알려 주었다.

**죽음은 답이 아니지만 소식은 된다.** 자식이 끝나면 기다리던 요청을 전부 그 자리에서 깨우도록
고쳤다. 이제 2번 걸음이 "MCP 가 끝났다 (code=null signal=SIGKILL)" 를 즉시 받는다.
이것은 시험용 손잡이만의 문제가 아니다 — MCP 를 부르는 쪽은 누구든 서버가 죽었을 때
그 사실을 알아야 한다.

## 지금 알려진 한계

- **판정은 이 연습에서 안 했다.** 끝난 자리의 완료가 0인 것은 그래서다 — 수집된 넷은 반납을
  기다리는 상태로 남겨 두었다. 되찾기만 재는 연습이라 그렇게 두었다.
- **영영 안 끝나는 쪽은 다시 돌려도 실패한다.** 그것이 맞는 결과다. 다시 돌리면 새 실행이
  하나 더 생기고 앞의 기록은 그대로 남는다.
- **만료를 기다리는 데 실제 1분이 든다.** 시계를 돌리지 않았다. 임대 만료는 시각으로
  판단하는 일이라, 시각을 속이면 그 판단을 안 잰 것이 된다.
