## 한 일

지도를 그리고, 나온 주소를 워커들이 나눠 빌려, **목적에 따라 산출물을 갈라** 받고, 판정을 붙여
반납하고, 분류용으로 내보냈다. 버튼만 썼다.

지도 → 1차 수집(http, 본문+링크) → **지도 다시** → 2차 수집(http, 본문+DOM) →
판정·반납 → 다시 대기 → 3차 수집(browser, 본문+그림) → 판정·반납 → 내보내기.

## 이 사이트에서 알게 된 것

**읽을 수 있는 sitemap 이 없다.** `/sitemap.xml` 은 못 읽었고 `/sitemap_index.xml` 은 넘어간 자리가
앞의 것과 같았다. 그래서 92곳 전부 **대표 페이지와 그 쪽들이 가리킨 링크**에서 나왔다.
지도는 못 읽은 파일을 오류로 남기고 "대표 페이지 한 장만 봤습니다 — 그 쪽이 가리키는 84곳의
내부는 안 봤습니다" 를 미확인 범위에 적었다.

**"수백" 은 이 도메인에서 안 나온다.** 한 번의 지도로 71, 수집한 링크를 넣고 다시 그려 92.
더 늘리려면 몰래 따라다녀야 하는데 그건 금지 사항이다. 1차 수집(2026-08-11)이 75곳을 찾고
`paused_incomplete` 로 멈춘 것과 견주면, 수는 비슷하고 **다른 점은 못 본 것을 안다는 것**이다.

**이 가게의 상품은 글이 아니라 그림이다.** 같은 상품 쪽을 두 방식으로 받아 나란히 놓으면:

| | 본문 | 산출물 |
|---|---|---|
| http | 753자 (머리글·차림표뿐) | 본문·링크 목록 |
| browser | 998자 (차림표가 다 펼쳐짐) | 본문 + **그림 37장** |

http 로는 카드가 무엇인지 알 길이 없다. 목적에 따라 산출물을 고른다는 말이 값을 하는 자리가
여기다 — 공지·목록 쪽은 본문+DOM 으로 충분했고, 상품 쪽은 그림이 있어야 봤다고 할 수 있다.

**정중함이 속도를 정한다.** 한 도메인이라 예약이 한 줄로 선다. 쪽당 12.4초였고, 71쪽에 877초,
21쪽에 267초가 들었다. **워커를 늘려도 빨라지지 않는다** — 셋으로 나눠도 같은 줄에 설 뿐이다.
워커를 나누는 뜻은 속도가 아니라 겹치지 않게 나눠 갖는 데 있다.

## 만드는 동안 실제로 걸린 것 — 결함 셋

**1. 오류 화면 판별이 71쪽 중 68쪽에 붙었다.** 이 사이트가 쪽마다 "저장되었습니다.
오류가 발생하였습니다." 라는 안내 문구를 숨겨 두고 자바스크립트로 꺼내 쓰기 때문이다.
96%에 붙는 표시는 아무것도 알려 주지 않고, 그 소음에 익숙해지면 진짜 오류 화면도 같이 넘긴다.
제목이나 본문 맨 앞 400자에 있을 때만 붙이도록 좁혔다. 69건으로 줄었다.

**2. 좁히고 보니 다른 사실이 있었다.** 그 68쪽의 본문이 742~1,444자뿐이고 전부 머리글이었다.
"오류 화면이라 짧은가" 와 "자바스크립트로 그려서 짧은가" 는 다른 사실이라 이름을 따로 줬다 —
`thin_text`, "받은 본문이 차림표 정도밖에 안 된다. browser 모드로 다시 보면 달라질 수 있다."
이름이 갈리자 다음에 할 일도 갈렸다.

**3. 브라우저 예약이 이동 시간을 잡아먹었다.** 워커 셋이 같은 도메인에 줄을 서자 22쪽 중
21쪽이 30초 초과로 죽었다. 예약을 "본문 이동에만" 걸도록 좁혔지만 그 기다림을 **요청을 가로채는
자리 안에서** 했고, 기다리는 동안 `page.goto` 의 시계는 그대로 흘렀다. 기다림을 이동 **밖**으로
옮겼다. 같은 49쪽을 다시 돌리니 실패 0, 쪽당 12.3초였다.

이 자리는 **세 번 고쳤다** — 요청마다 예약(시나리오 A 에서 발견) → 이동에만 예약 →
이동 밖에서 예약. 앞의 둘은 각각 "실제 사이트를 한 번도 안 열어 봐서", "워커 하나로만 열어 봐서"
못 봤다. 시험은 매번 통과했다.

**진행기 쪽 실수 하나도 적어 둔다.** 같은 워커 이름 `w8` 로 두 프로세스가 임대를 받아,
뒤엣것이 앞의 임대 번호를 기록에서 덮어썼다. 장부는 옳게 말했고("그 번호로 잡힌 항목이 없다")
틀린 것은 진행기의 기록이었다. 워커 이름은 에이전트가 관리할 몫이지 MCP 가 지켜 줄 수 있는
것이 아니다.

## 판정에 대해 — 두 번 적힌 66개

상품 쪽 66개에는 판정이 둘씩 있다. 첫 번째는 http 수집 뒤 경로 규칙으로 붙인 `상품` 이고,
두 번째는 브라우저 수집 뒤 `확인 필요` 다. **첫 번째가 성급했다** — 주소가
`/Product/Detail/` 이라고 해서 상품이라 적었는데, 그때 우리가 본 것은 차림표뿐이었다.

장부는 첫 번째를 지우지 않았다. 두 판정이 각자의 근거(서로 다른 실행의 산출물)와 함께 남아
있고, 내보낸 파일에도 둘 다 실린다. 읽는 사람이 그 어긋남을 그대로 본다 — 그것이 이 장부가
하려던 일이다.

다만 **두 번째 판정도 지금은 지나치게 조심스럽다.** 브라우저 수집에서 그림 37장을 받았으니
카드가 무엇인지는 본 셈인데, 내가 쓴 규칙이 본문 길이만 보고 `확인 필요` 로 보냈다.
규칙의 한계이지 도구의 한계가 아니다. 세 번째 판정을 덧붙이면 고쳐지고, 앞의 둘은 그대로 남는다.
