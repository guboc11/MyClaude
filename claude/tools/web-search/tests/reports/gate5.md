## 왜 통과가 아닌가

**잴 대상이 없다.** `#6` 에서 무키 검색 공급자 후보 아홉 곳을 실제로 두드려 보고 살아남은 곳이
0 이었다([decision.md](../spikes/search-provider/decision.md)). 그래서 `search` 버튼을 만들지
않기로 했고, 사용자가 유료 API 도입도 하지 않기로 확정했다. 게이트 5 가 요구하는
"5개 언어 50개 검색어 실전" 은 돌릴 대상 자체가 없다.

`#38` 의 완료 조건이 이 경우를 미리 적어 두었다 — **"공급자 미확정/불안정이면 이 태스크와 전체
개발 완료를 통과시키지 않는다."** 그대로 따른다. `#36`·`#37`·`#38` 은 완료로 넘기지 않고,
`#49` 최종 보고도 이 사실을 안고 간다.

## 그래서 무엇을 쟀는가

없는 것을 없다고 말하는지, 대신 가기로 한 길이 실제로 도는지 — 이 둘은 잴 수 있다.

```
node tests/gate5.mjs           # 종료 코드 0 통과 · 1 거짓말 발견 · 2 잴 대상 없음
node tests/gate5.mjs --json
```

종료 코드가 셋인 이유가 이 게이트의 전부다. **1 과 2 는 다르다.** 1 은 없는 기능을 있는 척했거나
대체 경로가 깨진 것이고, 2 는 거짓말은 없는데 잴 것이 없는 상태다. 둘을 같은 실패로 뭉뚱그리면
"고치면 되는 결함" 과 "고칠 수 없는 사실" 이 구별되지 않는다.

네트워크는 부르지 않는다. `add_urls` 는 URL 을 넣기만 하고 방문하지 않으므로 fixture 서버도
필요 없고, 정말 안 나갔는지는 `fetch` 를 세어 확인한다(G5-9, 접촉한 곳 0).

### 실제 수치

**증거는 그대로다.** `#6` 이 남긴 파일 17개의 크기와 지문이 하루 전 기록과 같고, 검증기 13항목이
전부 통과한다. 후보 9곳 모두 탈락 사유가 붙어 있고 살아남은 곳은 0 이다. 검증기는 네트워크를
다시 부르지 않는다 — 그날 무엇을 봤는지 확인하려는 것이지 오늘 다시 재려는 것이 아니다.

**없는 척이 아니라 없다.** 도구 목록에 `search` 가 없다. 목록에 있는 버튼은 하나하나 눌러 봤고
"아직 구현되지 않았습니다" 로 답한 것은 0개다 — 수를 못 박는 대신 **목록에 있는 것은 다 눌린다**
는 성질로 잰다. `search` 를 굳이 부르면 `isError` 로 막히며 `structuredContent` 가 아예 없다 —
"0건 성공" 으로 보일 칸(`queries_succeeded`·`new_urls`)이 응답 어디에도 없다.
코드에도 반쯤 만든 공급자가 없다:
`lib/search` 폴더 없음, `collector='search-provider'` 를 쓰는 파일 0개, `search_result`
artifact 를 쓰는 파일 0개. 이름은 스키마 상수 두 곳에만 남아 있다.

**대신 가는 길은 돈다.** 5개 언어(ko·en·ja·es·ar) 검색어 10개로 URL 19줄을 `add_urls` 에
`source_kind="search"`, `source_value=검색어` 로 넣었다. 고유 주소 14개 → item 14개,
검색어·URL 짝 18개 → 출처 18줄, 검색어가 안 붙은 item 0개. 네 검색어에서 함께 나온 주소 하나를
골라 되짚으니 검색어 4개가 다 나온다. 같은 묶음을 한 번 더 넣으면 새 item 0 · 중복 19 로
item 14개와 출처 18줄이 그대로다.

숫자 셋(19 · 14 · 18)이 서로 다른 것이 중요하다. 셋이 같으면 장부가 "받은 줄 수" 로 세는지
"검색어·URL 짝" 으로 세는지 구별되지 않는다. 그래서 첫 묶음에 같은 주소를 일부러 한 번 더
넣어 두었다.

## 못 재는 셋

**B1 — 검색을 한 번도 못 돌렸다.** search 실행 기록 0건. 성공·진짜 0건·차단·공급자 오류를
가르는 일은 결과가 있어야 성립한다.

**B2 — 되짚어지는 것은 검색어 하나까지다.** `search_result` artifact 0개이고, `sources` 칸은
`source_id·item_id·source_kind·source_value·source_item_id·discovered_at` 뿐이다.
`#37` 이 요구한 rank·제목 원문·설명 원문은 들어갈 자리가 없고, 이번에 보낸 locale 5종도
어디에도 안 남았다. **에이전트가 보낸 검색어는 남고, 그 검색이 어떤 순위로 무엇을 보여 줬는지는
안 남는다.** 지금 경로의 정확한 한계가 이것이다.

**B3 — 빈도는 하루로 못 낸다.** 반복 실행 자체가 없다. 이용 조건은 `#6` 이 하루치 한 번 모은 것이
전부다(robots 10건 · probe 3건 · 이용 조건 문서 4건).

## 사람이 정할 것 하나

**O1 — 도구 목록 응답이 상한 밖이다**(측정 당시 6,625바이트, 버튼이 아홉이 된 뒤 7,370바이트).
계약은 상한을 4,096바이트로 두고 "JSON-RPC 응답 한 줄 전체" 에 건다고 적었는데,
서버(`callTool`)도 계약 시험(C4)도 실제로는 **버튼 응답에만** 건다.
`tools/list` 에 담긴 것은 원문이 아니라 버튼 스키마라서, 상한의 취지("긴 원문을
응답에 싣지 않는다")와는 결이 다르다. 버튼이 늘수록 커지므로 그냥 두면 계속 벌어진다.

계약 문구를 "버튼 응답" 으로 좁히든 스키마 설명을 줄이든 **계약 개정 사안**이라 여기서 정하지
않았다. 얼어 둔 계약 파일을 게이트가 말없이 고치면 계약을 얼려 둔 뜻이 없어진다. 수치만 적어
올린다.

## 지금 알려진 한계

- **`search` 는 제품 기능이 아니다.** 이 MCP 는 검색을 하지 않는다. 후보 찾기는 에이전트가 자기
  `WebSearch` 로 하고, 결과 URL 을 `add_urls` 에 넣는다. 그 경로는 검색어까지만 남긴다(B2).
- **이 판정은 2026-08-12 시점이다.** robots 와 이용 조건은 바뀐다. 다시 볼 때는
  `node tests/spikes/search-provider/verify.mjs` 로 보존 증거부터 확인하고, 새로 재려면
  그때 다시 요청해야 한다.
- **없는 버튼은 `search` 하나다.** 이 보고를 쓴 뒤 `#41` 에서 `export` 가 붙어 공개 버튼은
  아홉이 됐고, 계약 시험이 실패하는 곳도 `search` 한 곳만 남았다.
